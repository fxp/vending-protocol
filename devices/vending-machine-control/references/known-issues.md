# 文档/Firmware 已知问题（10 处）

> 所有结论来自 NEWDEV № 01 实测数据（2026-04-30）。每条都有具体重现路径。

## #1 设备不校验 CRC（文档语焉不详）

CSV 只写"crc16"，没说哪种变种。穷举 18 种常见变种均不匹配输入帧。**结论：设备不校验输入 CRC**，填任意值都接受。

下位机自己发的应答用 **CRC16-XMODEM 大端**（poly `0x1021`, init `0`, 无反射, 不异或）。

**生产代码做法**：
- 偷懒方案：发送时填 `0x0000`
- 防御方案：仍按 XMODEM 大端算，万一未来 firmware 加校验也不怕

## #2 设备地址默认值不对

CSV 示例 `0x00000001`，本机实测 `0x00000000`（拨码开关决定）。

**做法**：地址必须做成可配置项，永远不要 hardcode。`probe.py` 自动遍历 0x00-0x03 找正确地址。

## #3 0x2B 应答结构与 CSV 不一致

CSV 写：
```
[1B 层数] + [N B 每层数] + [4B × 层数 (Y步数)] + [4B × 总货道 (X步数)]   = 180B
```

实际：
```
[1B 层数] + [N B 每层数] + [4B × 总货道 (X步数)]                        = 152B
```

**没有"每层 Y 步数"块**。每个货道一个 4 字节整数（看数值像 X 位置但无标识）。

## #4 0x24 应答字节 1 是层数不是状态码

CSV 写：byte[1] = 0x00 成功 / 0xFF 失败。

实际：byte[1] = 层数（如 7）。整体结构是 `[reserved] [layers] [motors_per_layer × N]`。

## #5 0x24 实际耗时 200s+

CSV 没说耗时。实测全扫描 36 货道 **202 秒**。

**做法**：
- timeout ≥ 300s
- 期间不要发别的指令（否则迟到的应答可能被 reset_input_buffer 冲掉）
- 失败用 0x2A 复位（**不是** 0x23）

## #6 0x29 echo 字段语义不明

测试矩阵：
| lane (hex) | echo (hex) | status |
|---|---|---|
| `0x0001` (=1) | `00 01` | 1 (无电机) |
| `0x0064` (=100) | `00 00` | 0 (有电机) |
| `0x0065` (=101) | `00 01` | 1 (无电机) |
| `0x00FF` | 无应答 | — |
| `0x0101`+ | 无应答 | — |

前 2 字节看起来像某种 `lane mod N` 映射，但**含义无法稳定推出**。

**做法**：只信第 3 字节状态。

## #7 0x35 type=1 横红外 — firmware 不实现

请求 `0x35 + payload=0x01`（横红外），应答 cmd 字段变成 `0x36`（其它 cmd 内容保留）。
其它 IR type（0/2/3）正常返回 `0x35`。

**判定**：firmware 不实现横红外，应答时占用了 `0x36` 作为占位 cmd。

**做法**：仅查 type=0/2/3。type=1 直接 skip。

## #8 0x04 永远报"无电机"（高危）

无论 lane 字段填 `0xFF`（跳过）还是真实 lane（如 100），都返回：
```
device_status=0x00 has_goods=0 can_dispense=no reason=0x02
```

但 lane=100 直接发 `0x28` 实际**出货成功**。

**做法**：**不要用 `0x04` 做出货预检**。直接发 `0x28`，看返回的 status 字节判断。

## #9 长操作期间 reset_input_buffer 会丢应答

`0x24` 这类 200s 才回的指令，期间如果代码用了 `ser.reset_input_buffer()`（pyserial 的 buffer flush），迟到的应答会被冲掉，永远收不到。

**做法**：
- 长操作期间用"被动监听不主动 flush"模式
- `assets/wm800.py` 的 `WM800Client.request()` 已避免这个问题
- 自己写代码注意 `reset_input_buffer()` 调用时机

## #10 5 条指令 firmware 不实现（黑名单）

| Cmd | 功能 | 测试 payload 数 | 应答 | 视觉验证 |
|---|---|---|---|---|
| `0x3D` | 平台电机直驱 | 7 | 0 | 9.9s 内平台一帧不动 |
| `0x23` | 伺服重启 | 7 | 0 | 30s 内伺服字节不变 |
| `0xBC` | 每层偏移 | 6 | 0 | — |
| `0x2C` | 改货道步数 | 5 | 0 | 0x2B 多次回读未变 |
| `0x35 type=1` | 横红外 | 3 | cmd 错 | — |

判定依据：每条都试过 5-7 种 payload 变种全部静默 + 应有的副作用从未发生。

**Firmware 信息**：
- 电机板 `VX9.2.0-2403209.Z.0-260320`（2024-03 编译）
- 平台板 `XYP.3.0-210918P.T.3-260317`（2021-09 编译）

平台板比电机板老 2 年半，那些"高级控制"指令大概率是后期加进 CSV 但老 firmware 没跟上的。商用机器的协议文档是**平台共用规范**，不是**实现清单**。

**做法**：永远不在生产代码里依赖这 5 条。
